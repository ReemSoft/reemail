# تطبيق بريد SaaS متعدد الشركات (Multi-Tenant Webmail)

## 1) الحقيقة التقنية أولاً — يجب أن تعرفها قبل البدء

منصة Lovable الحالية تعمل على **Cloudflare Workers**، وهذه البيئة **لا تدعم اتصالات TCP الخام** المطلوبة لبروتوكولات IMAP/SMTP/POP3. هذا ليس رأياً — هذا قيد تقني موثق.

يعني: **لا يمكن أن يعيش محرك البريد كاملاً داخل مشروع Lovable وحده**. نحتاج معمارية مكونة من جزأين:

```text
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  Lovable (Cloudflare)       │        │  خادم Node.js منفصل           │
│  - واجهة Gmail الحديثة       │◄──────►│  (VPS / Fly.io / Railway)    │
│  - لوحة تحكم الشركات         │  HTTPS │  - محرك IMAP/SMTP (OSS)      │
│  - قاعدة بيانات المستخدمين   │  API   │  - ImapFlow + Nodemailer     │
│  - المصادقة والصلاحيات       │        │  - كاش الرسائل / المرفقات    │
└─────────────────────────────┘        └──────────────────────────────┘
```

المكتبات OSS المقترحة (MIT — حرية كاملة للتعديل والبيع):

- **ImapFlow** (MIT) — عميل IMAP حديث بأداء ممتاز
- **Nodemailer** (MIT-0) — إرسال SMTP
- **mailparser** (MIT) — تحليل رسائل MIME والمرفقات

هذه هي نفس المكتبات التي تستخدمها Nylas وMailtrap داخلياً. أنت تملك الكود، لا اشتراكات ولا حدود.

## 2) نموذج SaaS متعدد المستويات

ثلاث طبقات من المستخدمين:


| الطبقة                | من                | ماذا يفعل                                             |
| --------------------- | ----------------- | ----------------------------------------------------- |
| **Super Admin**       | أنت (مالك المنصة) | إدارة الشركات، الاشتراكات، الحدود                     |
| **Company Admin**     | الشركة المشتركة   | يرفع شعارها، ألوانها، يضيف/يزيل عملاء (صناديق بريد)   |
| **End User (العميل)** | موظف/عميل الشركة  | يدخل بإيميله وباسووردة فقط، يرى واجهة تحمل شعار شركته |


**العلامة البيضاء (White-labeling):** كل شركة لها subdomain أو تخصيص كامل — الشعار، الألوان الأساسية، اسم التطبيق يظهر في واجهة عملائها.

## 3) الخطة المرحلية

### المرحلة 1 (نبدأ بها الآن في Lovable) — الأساس الكامل

- تصميم Gmail حديث، متجاوب مع كل الشاشات (موبايل، تابلت، ديسكتوب)
- نظام مصادقة كامل (Super Admin / Company Admin / End User)
- قاعدة بيانات: شركات، مستخدمون، إعدادات IMAP/SMTP (مشفرة)، شعارات
- لوحة تحكم Super Admin: إدارة الشركات
- لوحة تحكم Company Admin: رفع الشعار، الألوان، إضافة عملاء
- واجهة العميل: تسجيل دخول → صندوق وارد وهمي (Mock Data) يعرض شعار الشركة، البحث، الرسائل، الإرسال، المجلدات، المرفقات — **كل التفاعل يعمل على بيانات وهمية**
- طبقة API جاهزة `/api/mail/*` مع عقود واضحة (getMessages, sendMessage, ...) — واجهة موحدة تُستدعى من الأمام

### المرحلة 2 (خارج Lovable) — محرك البريد الحقيقي

- خادم Node.js مستقل يشغّل ImapFlow + Nodemailer + mailparser
- يستقبل استدعاءات من `/api/mail/*` ويترجمها لعمليات IMAP/SMTP فعلية
- كاش ذكي للرسائل (Redis) + WebSocket للتحديث الفوري
- نشر على Fly.io أو Railway (~5$/شهر للبداية)

**بمجرد اكتمال المرحلة 2، نبدّل رابط الـ API فقط في Lovable من Mock إلى الخادم الحقيقي — لا يتغير شيء في الواجهة.**

## 4) ما سأبنيه في هذه الجلسة (المرحلة 1)

1. تفعيل Lovable Cloud (قاعدة بيانات + مصادقة)
2. نظام الجداول:
  - `companies` (شعار، ألوان، اسم، subdomain)
  - `profiles` (ربط مع auth.users، company_id، الدور)
  - `user_roles` (super_admin / company_admin / end_user) — جدول منفصل آمن
  - `mail_accounts` (إعدادات IMAP/SMTP مشفرة بـ AES-GCM على الخادم)
  - `email_cache` (كاش للرسائل — يُملأ لاحقاً)
3. Design system حديث بألوان هادئة (نمط Gmail 2026)، خط عربي Cairo + إنجليزي Inter
4. صفحات:
  - `/` — Landing تسويقي للـ SaaS
  - `/auth` — تسجيل دخول ذكي (يوجّه حسب الدور)
  - `/admin` — لوحة Super Admin (قائمة الشركات)
  - `/company` — لوحة Company Admin (شعار، ألوان، عملاء)
  - `/mail` — واجهة البريد الشبيهة بـ Gmail (تحمل شعار الشركة تلقائياً)
5. مكونات الواجهة الكاملة: قائمة رسائل، عارض رسالة، Composer، مجلدات، بحث، Star، أرشفة، حذف، مرفقات (UI فقط)
6. Server functions مع عقود API نظيفة جاهزة للربط بالخادم الخارجي لاحقاً

## 5) قرارات تحتاج تأكيدك قبل التنفيذ

**أ) هل توافق على معمارية "Lovable + خادم Node منفصل"؟** 
هذا الطريق الوحيد لبناء محرك بريد حقيقي بـ IMAP/SMTP. البديل الوحيد الآخر هو Nylas/Mailgun (رفضته).

**ب) هل تريد أن أبني الآن المرحلة 1 كاملة كما وُصفت أعلاه؟**
أم تفضل تجزئتها؟ (مثلاً: نبدأ بواجهة العميل + بيانات وهمية فقط، ثم لوحات التحكم لاحقاً)

**ج) نطاق تخصيص العلامة (White-label):** شعار + اسم فقط؟ أم شعار + ألوان + subdomain مخصص لكل شركة؟

عندما تجيب على هذه الثلاث، أبدأ التنفيذ فوراً.
